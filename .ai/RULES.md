# Project rules

1. Provide a standalone, reproducible research workflow; the course checkout and the salary project are references, never runtime dependencies.
2. Record data source, actual publication/availability time, retrieval time, licensing and gaps. Never infer COT availability solely from its observation date. Exclude unconfirmed periods rather than silently backdating them.
3. Define feature cutoff, ETF exchange calendar, signal, execution, five-session target and adjustment conventions. Crypto candles must have closed before the feature cutoff. Do not fill future observations backwards.
4. Split chronologically and purge target intervals that cross split boundaries. Fit preprocessing on training data; select models and strategy thresholds without the holdout.
5. Record starting capital, position sizing, overlapping positions, turnover, fees and slippage. Compare against a stated baseline on the same period and present limitations, not promises.
6. Treat external files and provider responses as untrusted. Log failures and missing data explicitly; preserve reproducible local snapshots outside version control.
7. Use concise, scoped changes and meaningful checks. Do not add cloud, orchestration, telemetry, or RAG services merely to make a checklist look complete.
8. Keep the implementation plan and memory current with dated evidence. Design decisions and future work are not evidence of completed tests, integrations, or financial results.
9. Spec-driven work: update the relevant spec and acceptance scenarios for behavior changes, implement, then validate the behavior. Only report OpenSpec CLI validation if actually run successfully.
10. Use Superpowers for applicable planning, delegation, debugging and verification; use Ponytail's smallest complete solution without dropping required validation or financial correctness. Higher-priority instructions prevail.

11. Place documentation of implemented project behavior for both people and agents in `docs/`: use Diátaxis (tutorials, how-to guides, reference and explanation) as a practical guide, with ADRs, architecture, runbooks and changelog where appropriate. Link to a single canonical account rather than duplicating facts.
12. Keep agentic operations under `.ai/`: backlog, implementation and next-step plans, session prompts and management, rules, roles and project memory. Project requirements remain in `openspec/`. Link operational records to relevant project documentation and evidence.
13. English is the primary documentation language. Maintain Russian `.ru.md` mirrors for the main human-facing documents, with reciprocal language-switch links; update both when their meaning changes and explicitly flag any translation that is out of date. Do not translate agent-only operational artifacts by default.
14. Parallel sessions use object-level locks as the default in a shared workspace. Claim exact files or a named integration contract before editing, check owner metadata, and release only locks held by the current session after handoff. Never break a lock based only on age. Use the global `agent-session-lock` skill where its repository-backed mechanism applies; this workspace has no Git repository, so use `scripts/object_lock.py` as the local fallback. For critical work that cannot wait on an object lock, use a separate Git worktree if the project has a Git repository; otherwise queue the work. Do not run two writers in one worktree.
15. Every parallel-session prompt must name one owner, exact files/objects, required lock slug, dependencies/interfaces, forbidden edits, handoff format and verification expectations. Keep shared writable files under one owner; other sessions can review read-only or work in isolated worktrees.
16. Keep `Makefile` as the discoverable human interface for short, common project tasks and general local operations. Put multi-step, parameterized, reusable, and agent/session coordination workflows in `Justfile`; let Make targets delegate to Just for shared complex behavior rather than duplicating recipes. Keep common Make targets usable without Just where practical, document prerequisites, and validate both command surfaces after changes. Read `.ai/.codex/skills/build-command-interface/SKILL.md` before changing either file.
