# Capstone verification

1. Read `AGENTS.md`, `.ai/IMPLEMENTATION_PLAN.md`, `.ai/RULES.md`, `.ai/roles/ROLES.md`, `.ai/memory/PROJECT_MEMORY.md`, `.ai/BUGS.md`, `.ai/BACKLOG.md`, the project specification and the parallel-session coordination instructions. Inspect active session/object ownership. Acquire locks for every shared file you will edit; preserve all unrelated staged and unstaged work.
2. Verify the current official course rubric and submission/peer-review rules from their primary source. Record the source URL and check date. Compare each criterion with a concrete artifact and observed result; distinguish reviewer judgment, requirements, implementation evidence and actual outcome. If the source cannot be checked, label it unverified and use the checked-in rubric only as a dated baseline.
3. Run the documented project verification command, relevant focused checks, and the offline/local-snapshot and end-to-end workflows where configured inputs exist. Record exact commands, results, skips, warnings and blockers. Never substitute synthetic fixtures or demos for real-data evidence. Do not run network acquisition unless the source/retrieval workflow is explicitly part of the requested verification and is safe to execute.
4. Inspect point-in-time availability, release evidence, exchange/crypto cutoffs, chronological splits and purging, holdout isolation, simulation costs/capital/benchmark, source terms/provenance, configuration, documented commands, secrets and ignored data/artifacts. Cross-check README and `docs/` claims against run artifacts; check reciprocal language links and consistency of main `.ru.md` mirrors.
5. Report every criterion as verified, partial, open, blocked or deferred, with an evidence link and concise reason. Include actual presentation, submission and peer-review obligations without assuming completion. A test file, design, synthetic run or code path is not proof of a real-data experiment. Record reproducible defects in `.ai/BUGS.md`, link actionable fixes from `.ai/BACKLOG.md`, and mark bugs verified only after their stated acceptance check passes.
6. Refresh [`docs/COURSE_CRITERIA_STATUS.md`](../../../docs/COURSE_CRITERIA_STATUS.md) and its Russian mirror from the current official rubric and the criterion-level evidence matrix in `openspec/specs/capstone/spec.md`. Record the check date, source, total rubric-item counts per status, the six bold minimum-score criteria individually, and the separate submission, presentation and three-peer-review obligations. Link evidence and the full matrix instead of duplicating all criterion text. Keep statuses synchronized; if the official rubric cannot be checked, mark the snapshot unverified and retain its prior date. Do not count code-only or synthetic evidence as a passed course outcome.
7. In the final session response, include a compact **Course criteria coverage** section: the date/source checked, counts of verified/partial/open/blocked/deferred criteria, the six bold gate statuses, any submission/presentation/peer-review status, and direct links to the status snapshot and full matrix. State that partial means implementation evidence exists but course credit/outcome is unverified. Never report only a file link without the coverage summary.
8. Append a dated evidence entry to `.ai/IMPLEMENTATION_PLAN.md` (and update status/backlog only when their current claims need correction). State commands, actual outcomes, material limitations and remaining blockers. Release only locks acquired by this session after handoff. Do not commit, publish, or modify a remote as part of verification.
