# Capstone verification

1. Read `AGENTS.md`, `.ai/IMPLEMENTATION_PLAN.md`, `.ai/RULES.md`, `.ai/roles/ROLES.md`, `.ai/memory/PROJECT_MEMORY.md`, `.ai/BUGS.md`, `.ai/BACKLOG.md`, the project specification and the parallel-session coordination instructions. Inspect active session/object ownership. Acquire locks for every shared file you will edit; preserve all unrelated staged and unstaged work.
2. Verify the current official course rubric and submission/peer-review rules from their primary source. Record the source URL and check date. Compare each criterion with a concrete artifact and observed result; distinguish reviewer judgment, requirements, implementation evidence and actual outcome. If the source cannot be checked, label it unverified and use the checked-in rubric only as a dated baseline.
3. Run the documented project verification command, relevant focused checks, and the offline/local-snapshot and end-to-end workflows where configured inputs exist. Record exact commands, results, skips, warnings and blockers. Never substitute synthetic fixtures or demos for real-data evidence. Do not run network acquisition unless the source/retrieval workflow is explicitly part of the requested verification and is safe to execute.
4. Inspect point-in-time availability, release evidence, exchange/crypto cutoffs, chronological splits and purging, holdout isolation, simulation costs/capital/benchmark, source terms/provenance, configuration, documented commands, secrets and ignored data/artifacts. Cross-check README and `docs/` claims against run artifacts; check reciprocal language links and consistency of main `.ru.md` mirrors.
5. Report every criterion as verified, partial, open, blocked or deferred, with an evidence link and concise reason. Include actual presentation, submission and peer-review obligations without assuming completion. A test file, design, synthetic run or code path is not proof of a real-data experiment. Record reproducible defects in `.ai/BUGS.md`, link actionable fixes from `.ai/BACKLOG.md`, and mark bugs verified only after their stated acceptance check passes.
6. Refresh [`docs/COURSE_CRITERIA_STATUS.md`](../../../docs/COURSE_CRITERIA_STATUS.md) and its Russian mirror from the current official rubric and the criterion-level evidence matrix in `openspec/specs/capstone/spec.md`. Record the check date, source, total rubric-item counts per status, the six bold minimum-score criteria individually, and the separate submission, presentation and three-peer-review obligations. Link evidence and the full matrix instead of duplicating all criterion text. Keep statuses synchronized; if the official rubric cannot be checked, mark the snapshot unverified and retain its prior date. Do not count code-only or synthetic evidence as a passed course outcome.
7. In the final session response, include a compact **Course criteria coverage** section: the date/source checked, counts of verified/partial/open/blocked/deferred criteria, the six bold gate statuses, any submission/presentation/peer-review status, and direct links to the status snapshot and full matrix. State that partial means implementation evidence exists but course credit/outcome is unverified. Never report only a file link without the coverage summary.
8. Append a dated evidence entry to `.ai/IMPLEMENTATION_PLAN.md` (and update status/backlog only when their current claims need correction). State commands, actual outcomes, material limitations and remaining blockers. Release only locks acquired by this session after handoff. Do not commit, publish, or modify a remote as part of verification.

## Network and source-access diagnostics

Use this workflow when DNS, package installation, GitHub, or market-data acquisition appears unavailable.

Reusable project checks live in `scripts/check_external_access.py` and `scripts/check_clean_install.py`. Run the first from the same network boundary as acquisition; it performs bounded requests (including only a short recent Stooq GLD sample) and deliberately does not retry HTTP 429. Run the second when package access is available; it installs `uv.lock` with the `dev` extra into a temporary environment with a fresh temporary uv cache, imports core/dev packages, checks notebook-format support and an XNYS session, and removes both temporary paths when complete.

For FRED, the reachability probe also tries a bounded `curl` request if Python `urllib` fails. It discards the response body and reports the curl HTTP status and remote IP separately, preserving both outcomes so a client/CDN-edge discrepancy is not mislabeled as total host unavailability. This checks only the landing page, not FRED series API access or vintage suitability.

1. **Identify the execution boundary first.** Run a resolver lookup and a bounded HTTPS request in the same environment that failed. If sandboxed probes report socket permission errors, do not label that a host or machine DNS outage. Repeat the minimal probes through an explicitly approved non-sandboxed diagnostic path; record which boundary each result came from.
2. **Separate failure layers.** Check name resolution, TCP/TLS reachability, and HTTP status independently. `NXDOMAIN`/`SERVFAIL`, timeout, connection refusal, certificate failure, HTTP 429, HTTP 403, and HTTP 5xx mean different things. A successful DNS lookup does not prove HTTPS or data access; an HTTP response proves host reachability but a 429/403 does not prove endpoint usability.
3. **Probe independent control and data endpoints.** Include a neutral control such as GitHub and the package index (PyPI), then the primary data provider(s), then plausible alternatives. For this project those may include CFTC website/archive and PRE API, Yahoo Finance, FRED, Stooq, and Alpha Vantage. Keep requests bounded; never bulk-download during a connectivity check.
4. **Inspect local network context read-only.** Where permitted, record active interface/default route, resolver configuration, VPN/proxy state and relevant environment proxy settings. If the sandbox prevents system tools or socket access, report that limitation instead of inferring a device configuration. Do not change DNS, VPN, proxy, firewall, or system network settings without explicit authorization.
5. **Evaluate a data fallback before adopting it.** Verify the required instruments and date coverage, OHLCV fields, raw/adjusted price semantics, corporate actions, timezone/calendar, rate limits and terms. For COT, prefer CFTC's primary records and preserve report-specific publication availability. A reachable service is not automatically a fit-for-purpose or point-in-time-safe source.
6. **Record reproducible evidence.** Log timestamp and timezone, environment/boundary, exact host/path (omit secrets and API keys), command, resolver/remote IP when available, DNS result, TLS result, HTTP status, and interpretation. Do not place tokens or full sensitive URLs in skill notes or project logs. Repeat only when state may have changed or when a targeted next step depends on the result.
7. **Choose the next action from evidence.** If all name lookups fail only inside the sandbox but succeed outside, classify as sandbox egress/resolver restriction and use the approved network path. If lookups fail in both contexts, inspect resolver/network state with the device owner or network administrator. If DNS succeeds but HTTPS fails, investigate routing, proxy, TLS or provider filtering. If package index responds, retry the clean locked installation as a separate step; if a provider returns 429, honor its limits and do not disguise it as DNS failure.

Keep acquisition and clean-install gates independent. Continue offline deterministic QA while either external gate is unavailable; never replace real observations with synthetic fixtures or call cached dependencies a clean install.
