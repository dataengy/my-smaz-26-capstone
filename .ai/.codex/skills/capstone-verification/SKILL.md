# Capstone verification

1. Read `AGENTS.md`, `.ai/IMPLEMENTATION_PLAN.md`, `.ai/RULES.md`, `.ai/roles/ROLES.md`, `.ai/memory/PROJECT_MEMORY.md`, `.ai/BUGS.md`, `.ai/BACKLOG.md`, the project specification and the parallel-session coordination instructions. Inspect active session/object ownership. Acquire locks for every shared file you will edit; preserve all unrelated staged and unstaged work.
2. Inspect all Git worktrees and branches (`git worktree list`, branch/status for each). Establish which checkout owns the requested work and compare any test or source file implicated by backlog/bug claims across branches. Run acceptance checks in the owning worktree and target interpreter; a pass on one branch does not validate another branch's copy. Never correct or resolve a bug record based only on evidence from a different branch.
3. Verify the current official course rubric and submission/peer-review rules from their primary source. Record the source URL and check date. Compare each criterion with a concrete artifact and observed result; distinguish reviewer judgment, requirements, implementation evidence and actual outcome. If the source cannot be checked, label it unverified and use the checked-in rubric only as a dated baseline.
4. Run the documented project verification command, relevant focused checks, and the offline/local-snapshot and end-to-end workflows where configured inputs exist. For the standard local acceptance path, inspect `Justfile` and `Makefile`; `just verify` should run `just doctor`, `just lock-check`, `just compile`, then `make test`. Run `make test` separately only when its standalone result is needed or `just verify` cannot complete, and avoid repeating expensive checks without a reason. Record exact commands, results, skips, warnings and blockers. Never substitute synthetic fixtures or demos for real-data evidence. Do not run network acquisition unless the source/retrieval workflow is explicitly part of the requested verification and is safe to execute.
   - Treat `just doctor` output (`python3 --version`, `uv --version`, `make --version`, `just --version`) as host-tool discovery, not proof of the Python interpreter used by project commands. State the actual interpreter/environment used by `uv run` or pytest when that is observable; if user-provided output does not identify it, say so rather than infer it from the host Python version.
   - `just lock-check` uses `uv lock --check --offline` and verifies lock consistency without installing dependencies. `just compile` runs `uv run --locked --no-sync python -m compileall -q src scripts tests`; it checks syntax but does not prove imports, source access or research readiness. `make test` runs the pytest suite through the locked project environment; report pass/fail counts, skips and warning counts from the actual summary.
   - If `just verify` completes successfully, report the four stages and test summary as observed. If it stops early, identify the failed stage and do not imply later stages ran. Keep the opt-in live-provider, origin-clone and real-data checks distinct from the default suite; do not describe skipped checks as passing.
   - For source replay idempotency, run the focused offline replay check. On unchanged checksum-valid snapshots and the same config, compare repeated `load_sources` results, assert that neither market/COT snapshots nor sidecars changed, and fail the test if a provider request occurs. Confirm deterministic feature output and clear rejection of duplicate market dates and COT report keys. Treat this as offline replay evidence, separate from cache-aware refresh and live source acquisition.
5. Inspect point-in-time availability, release evidence, exchange/crypto cutoffs, chronological splits and purging, holdout isolation, simulation costs/capital/benchmark, source terms/provenance, configuration, documented commands, secrets and ignored data/artifacts. Cross-check README and `docs/` claims against run artifacts; check reciprocal language links and consistency of main `.ru.md` mirrors.
6. Report every criterion as verified, partial, open, blocked or deferred, with an evidence link and concise reason. Include actual presentation, submission and peer-review obligations without assuming completion. A test file, design, synthetic run or code path is not proof of a real-data experiment. Record reproducible defects in `.ai/BUGS.md`, link actionable fixes from `.ai/BACKLOG.md`, and mark bugs verified only after their stated acceptance check passes.
7. Refresh [`docs/COURSE_CRITERIA_STATUS.md`](../../../../docs/COURSE_CRITERIA_STATUS.md) and its Russian mirror from the current official rubric and the criterion-level evidence matrix in [`openspec/specs/capstone/spec.md`](../../../../openspec/specs/capstone/spec.md). Record the check date, source, total rubric-item counts per status, the six bold minimum-score criteria individually, and the separate submission, presentation and three-peer-review obligations. Link evidence and the full matrix instead of duplicating all criterion text. Keep statuses synchronized; if the official rubric cannot be checked, mark the snapshot unverified and retain its prior date. Do not count code-only or synthetic evidence as a passed course outcome.
8. Before handoff, read `.ai/STATUS.md`, `.ai/NEXT_STEPS.md` and `.ai/BACKLOG.md` again and reconcile their current claims with this run. Update status/next steps only where newer evidence makes them stale; keep `.ai/BACKLOG.md` as the canonical project queue. Do not copy the entire project backlog into the session response.
9. In the final session response, include a **Session handoff** with these distinct answers:
   - **Where we are:** current research/workflow state and latest verification evidence, with material blockers.
   - **Course criteria coverage:** date/source checked; verified/partial/open/blocked/deferred counts; statuses of all six bold gates; submission, presentation and peer-review status; links to the [coverage snapshot](../../../../docs/COURSE_CRITERIA_STATUS.md) and [full matrix](../../../../openspec/specs/capstone/spec.md#course-acceptance-evidence-matrix). State that partial means implementation evidence exists but course credit/outcome is unverified.
   - **What happens next:** the next one to three actionable tasks in dependency order, sourced from `.ai/NEXT_STEPS.md` and `.ai/BACKLOG.md`; state the external input that blocks any gated task.
   - **What remains in this session:** list only work still required to fulfill the active user request or handoff; if none, say so. Keep longer-term project backlog separate from unfinished session work.
   - **Finalize or continue:** recommend finalizing when the active request is complete and no necessary authorized work remains; recommend continuing when this session still has concrete, unblocked work. If continuing, name the first action. Do not imply a project is complete just because the current session can be finalized.
10. Append a dated evidence entry to `.ai/IMPLEMENTATION_PLAN.md` (and update status/backlog only when their current claims need correction). State commands, actual outcomes, material limitations and remaining blockers. Release only locks acquired by this session after handoff. Do not commit, publish, or modify a remote as part of verification.
11. When a user provides command output, treat it as evidence for that command only. Check the actual target interpreter/environment path and package versions; distinguish lock resolution, dependency installation, import success, provider reachability, snapshot creation, and real experiment execution. Update the P0 status when new evidence still leaves real market snapshots or sufficient COT release history unavailable.
12. When source access or acquisition is explicitly in scope, first use the project's intended interpreter and perform bounded DNS/HTTPS checks for Yahoo Finance and CFTC. A short Yahoo chart request and an HTTP status/header or small-range CFTC archive request are enough to establish current reachability; do not download the full multi-year dataset as a connectivity probe. If the bounded check succeeds, run the configured downloader and validate every snapshot's SHA-256 sidecar, source/ticker metadata, request-start timestamp, schema, date range, duplicates and completed-bar cutoff before treating it as usable. If a CFTC archive request returns 403, report it as an HTTP access denial, do not retry through proxies or alternate identities, and preserve any already-valid market snapshots. If access fails, do not start or repeat bulk acquisition; report the exact failure and continue only with read-only validation of existing local snapshots. A valid Yahoo price cache alone does not satisfy the CFTC or research gate.
13. Prefer the opt-in `make test-source-smoke` for that preflight when it exists. It must remain bounded, use the configured traded targets plus one representative/current CFTC archive, read only small response prefixes, and never save snapshots. Keep it opt-in so default smoke tests remain offline. If it fails on DNS or access, record the provider-specific result and do not invoke the bulk downloader; if it passes, proceed to the normal configured download and validate the resulting snapshots separately. `make test-smoke` only confirms the default offline smoke path and is not evidence of live provider access.
