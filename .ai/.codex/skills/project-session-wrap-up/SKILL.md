# Project session status and wrap-up

Use when the user asks where the project stands, what remains, or whether a session can be finalized. Also use after a requested commit/push workflow when the result needs a clear handoff. This skill reports state and protects concurrent work; it does not itself authorize publishing or finalizing an outstanding request.

1. Read `AGENTS.md`, `.ai/IMPLEMENTATION_PLAN.md`, `.ai/RULES.md`, relevant roles, project memory, and the capstone spec. Load the Git/GitHub workflow and periodic commit/push guidance when publication or scheduling is involved.
2. Inspect `git status --short --branch`, current branch and upstream, origin URL, recent commits, staged/unstaged/untracked paths, and ahead/behind counts. Run `git worktree list` and inspect each listed worktree's branch and status for session-owned or conflicting changes; don't infer the active branch from user-pasted output if the shell is in another checkout. Compare the relevant file in every active branch/worktree before describing its state. Report local-ahead commits separately from the verified remote tip. Use `git ls-remote` when reachable; never present a local hash as a published hash. If network access fails, say the remote tip could not be independently verified.
3. Inspect `.ai/.locks/*/owner.json` before proposing commits or edits. Preserve files under active locks. Do not treat age, an inaccessible process listing, or a missing response as proof a lock is stale; never release another session's lock. If the shared index contains locked or concurrently owned files, do not reset, restage, commit, or push it. Wait for handoff or ask whether to narrow scope; an explicit request to include all new work does not transfer another session's file ownership.
4. If a periodic LaunchAgent is part of the task, inspect its plist and `launchctl print gui/$(id -u)/<label>`. Confirm its executable and script paths point into the current project checkout, check its interval, and distinguish `state = not running` before the first interval from failure. Do not manually invoke a scheduled cycle just to inspect it, since it may commit and push.
5. For `$smart-commit-and-push all new`, treat the requested scope as all current changes, equivalent to `--commit-all`, while still excluding secrets, generated data/artifacts, and unrelated concurrent work. First review exact staged, unstaged, and untracked paths and check environment/config files for populated credentials without printing their values. Split commits by category when the set is safe and unlocked. Run project-configured checks when authorized by the invoked smart-commit workflow; never claim unrun checks passed. Do not rewrite already-pushed commits. The explicit push request authorizes pushing the resulting requested commits; do not ask a second generic push question.
6. Resolve the hosting provider from the configured remote and project workflow. After a successful push, open that provider's CI page (GitHub Actions for GitHub, GitLab pipelines/jobs for GitLab) when browser access is available. Do not report a CI run or remote hash without observing it. If browser or network access is unavailable, state that plainly.
7. Distinguish project completion from session completion. State what is verified, what remains in the backlog, what is pending in this session, and whether another session owns an active lock. A session can be finalized while the project has backlog, but not while this session has an outstanding requested action or unhanded-off changes.
8. Give a concise handoff answering these questions explicitly: where are we; what happens next (one to three smallest dependency-ordered tasks); what remains in this session; and should we finalize or continue? Include completed and verified work, uncommitted changes and their owners/worktrees, local commits not yet pushed, installed automation state, and blockers. Separate project backlog from work still required by the active request. Say the session is ready to finalize only when no requested action remains in this session and any changed files have a clear owner and handoff.
9. If the user asks only for status or finalization, do not commit, push, force-push, install or remove a LaunchAgent, or change files owned by another session. If they explicitly authorize publication, use the Git/GitHub workflow, review exact paths, honor filesystem/network restrictions, and verify the remote tip after push. Never claim the scheduler is installed merely because its installer exists, or claim it has run before its first interval.
10. If the user supplies new execution evidence while asking for status, treat it as steering for the active project handoff: reconcile `STATUS.md`, `NEXT_STEPS.md`, `BACKLOG.md` and the dated implementation evidence, but respect object locks and coordinate with current owners instead of editing locked files. Separate project incompleteness from session finalizability; name the P0 data/COT blockers before suggesting session closure.
11. If verification or a reported test result conflicts with the current backlog, bug register, branch, or worktree, inspect the exact current test/code diff and rerun the smallest relevant check in the correct worktree before changing any pass/fail claim. Report the branch and interpreter/environment used; never mark a bug fixed from another branch's result alone.
12. For a blocked real-data workflow, distinguish runtime source reachability, successful download, snapshot integrity, usable row-level coverage, and reproducible downstream results. When network access is being retried, use a bounded probe first; launch bulk acquisition only after the probe succeeds. A later DNS failure does not invalidate a previously completed download, and files on disk do not prove they are usable: inspect current paths, hashes/sidecars, provenance, required symbols/years, nulls, duplicates, date coverage, and source freshness. Reconcile contradictory status entries against those concrete artifacts and dated command output before reporting the blocker or editing status documents.
13. For COT evidence, distinguish a report-specific publication record from a tentative release calendar, an archive observation date, or an archive “updated” footer. A contemporaneous CFTC notice can support a row when it identifies the report or states it was issued that day and the report date is independently matched. From the official CFTC PRE dataset launch onward, row-specific Socrata `:created_at` metadata can also support report availability when both configured contract rows are present and agree; corroborate against contemporaneous notices where available. Exclude pre-launch bulk-import timestamps as publication evidence. When relying on PRE metadata, verify unchanged `:created_at`/`:updated_at`, exact model-field matches against hash-verified annual archives, and save the query, raw response hash and retrieval time. Describe `:created_at` as public dataset row creation, not a preserved access log or necessarily the original publication instant. Set `available_at` conservatively after the evidence date and describe it as an eligibility cutoff, not an exact publication instant. Preserve query provenance because current API system metadata is not an immutable historical snapshot. Keep remaining gaps, row coverage, and vintage limitations explicit; do not claim evidence alone establishes model or strategy results.
14. If the user asks whether to finalize while the project is blocked, answer separately whether the project is complete and whether this session's requested work is complete. A session may be finalized with project backlog only after all requested checks/edits are done, changed paths are handed off, and no held lock or unresolved concurrent ownership belongs to this session. State the smallest dependency-ordered next steps, avoid promising a future automatic retry, and do not claim source access will recover without new evidence.
15. When reporting project status, use this compact emoji legend consistently in status documents: 🟢 verified complete, 🟡 partial/in progress, 🔴 blocked, ⏸️ deferred. Keep an explicit status word and evidence next to each marker; emojis are navigation aids, never evidence or a replacement for the status explanation. Preserve English as the primary docs language and update the `.ru.` mirror when a main human-facing document changes.
16. For downloader work, distinguish cache-aware repeatability from offline replay and from a successful live refresh. Verify that cache reuse checks checksum, source/provider provenance, schema, duplicate/order constraints, completed-bar cutoff, finite prices and requested date coverage; verify the configured freshness policy for mutable current-year archives. Test unchanged valid cache skip, invalid cache refresh, forced refresh, and rejection of malformed responses before replacement. Document what `--force` means, per-source logging and final counts. Run the bounded source smoke immediately before bulk acquisition; if it fails, do not start bulk download and do not infer current availability from an earlier user-pasted smoke result. After a successful download, independently inspect hashes, provenance, rows, dates, nulls and COT coverage. Preserve prior files and do not claim the full research experiment from download success alone.
17. After the user reports or invokes a download, inspect the actual local snapshots and sidecars independently: expected provider/ticker, checksums, schema, date range and earliest provider-available date, sorted unique dates, completed observations, finite/non-null required prices, and parseable COT archives with both target contracts. Treat the terminal download summary as evidence of command behavior, not as a substitute for reading the resulting files. For a repeated run, record downloaded/skipped/failed separately; `0 downloaded` can be the expected idempotent outcome when all 19 source caches validate. Never replace a usable snapshot just to make the count nonzero.
18. For expanded COT evidence, inspect the frozen query/provenance, retrieval timestamp and payload hash; count paired contract rows and distinct report dates; check post-launch scope, unchanged `:created_at`/`:updated_at`, both-contract completeness, exact match to modeled fields in the hash-verified annual archives, and the conservative eligibility cutoff. Explain that Socrata `:created_at` is a public-dataset row-creation timestamp, not a preserved historical access log or guaranteed original release instant. Keep pre-launch bulk imports and mismatches excluded. Distinguish a bounded, defensible multi-year evidence window from complete historical coverage.
19. If a full real-data run is produced, inspect its coverage gate, frozen input inventory and hashes, chronology/purge boundaries, validation-only selection and held-out period. Re-run from the saved input bundle or use its exact reproducibility command, compare declared numerical output hashes, and verify reported metrics directly from artifacts before updating status. State the selected baseline/model and net-of-cost results candidly; do not describe a negative or marginal result as strategy success. A reproducible run can close the experiment-execution blocker while leaving broader COT history, data-vintage, rights and course-deliverable gaps open.
20. Before handoff, check the active lock owners again. Do not edit or summarize a parallel session's files as integrated until its owner releases the relevant lock or explicitly hands off. Update only files owned by the current session, preserve historical entries, reconcile current status against artifacts, synchronize human-doc mirrors, and release only current-session locks. If project blockers remain but this session's requested verification, edits and handoffs are complete, state that the session can be finalized while the project itself remains in progress.
